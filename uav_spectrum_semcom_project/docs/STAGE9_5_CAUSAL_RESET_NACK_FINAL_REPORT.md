## 1. 研究结论

阶段9.5建立了不允许发送端读取接收端内部状态的因果反馈状态机，并加入明确计费的32 bit `RESET-NACK`。冻结后的确认实验通过全部预注册门槛。

在异步启动公告退化和完全不可用时，RESET-NACK相对无NACK安全协议分别提高6.981和12.945个百分点clean，同时总bit分别下降8.527%和17.191%。这说明阶段9.4的主要问题不是16 bit恢复标签，也不是必须永久接受30景等待，而是缺少一条显式、可计费的上下文失效反馈路径。

该结果只适用于“异步启动公告失败，但普通请求—响应反馈链路仍可用且按既定概率丢包”的条件，不适用于整个反馈发射机失效。

## 2. 协议机制

发送端状态只允许由成功送达的启动状态、ACK、RESET-NACK和看门狗响应改变。接收端内部的 `restore()`、`update()` 返回值只用于决定接收端是否生成响应帧，不得直接成为发送端知识。

32 bit RESET-NACK包含：

| 字段 | 位宽 |
|---|---:|
| 魔数 | 4 bit |
| 版本 | 2 bit |
| 原因 | 2 bit |
| 接收端 boot ID | 16 bit |
| 目录版本 | 8 bit |

当失活接收端成功收到普通更新时：

1. 接收端拒绝执行更新；
2. 生成并计费RESET-NACK；
3. 只有NACK成功送达，发送端才获得 boot ID与目录状态；
4. 下一次发送使用阶段9.3的16 bit恢复会话标签；
5. NACK丢失时继续等待更新重试或30景看门狗。

## 3. 实验设计

复用阶段9.1的1000景任务、四类故障剖面和双向丢包参数。所有策略使用相同标签恢复和相同因果状态机：

- causal HBW30 + RESET-NACK；
- causal HBW30，无NACK；
- causal fixed10 + RESET-NACK；
- causal boot-event + RESET-NACK。

开发集为每类80条轨迹，确认集为每类120条轨迹。确认总规模为480条轨迹、480,000景。所有比较使用共同随机数配对和预注册bootstrap区间。

## 4. 确认结果

| 故障剖面 | 候选clean | 候选bit/景 | NACK帧总数 | 相对无NACK clean | 相对无NACK bit |
|---|---:|---:|---:|---:|---:|
| normal_sparse | 98.983% | 8.192 | 6 | 0.000个百分点 | +0.020% |
| normal_mobile | 96.952% | 14.815 | 76 | 0.000个百分点 | +0.133% |
| emitter_degraded | 89.028% | 13.596 | 989 | +6.981个百分点 | −8.527% |
| emitter_failed | 81.167% | 13.176 | 2,017 | +12.945个百分点 | −17.191% |

故障条件下出现“clean提高且bit下降”，原因是及时NACK减少了长时间失活、无效等待和后续完整恢复，不是NACK本身具有压缩作用。

### 4.1 相对无NACK

- emitter_degraded：clean改善95%区间为6.441至7.537个百分点；
- emitter_failed：clean改善95%区间为12.247至13.634个百分点；
- 正常两类clean完全一致，bit增加均低于0.14%。

### 4.2 相对因果fixed10

- normal_sparse：bit节省区间为31.354%至32.974%，clean提高1.969至2.438个百分点；
- normal_mobile：bit节省区间为17.012%至19.131%，clean提高7.347至8.078个百分点；
- emitter_degraded：bit约节省22.84%，clean平均低0.546个百分点且区间包含接近0；
- emitter_failed：bit约节省26.13%，但clean低8.613个百分点。

因此候选仍不是 fixed10 的无条件替代方案。启动公告完全失效且高可靠性优先时，fixed10仍提供更高clean，但消耗更多bit。

### 4.3 相对因果boot-event

- emitter_degraded：clean提高1.531个百分点，bit增加4.064%；
- emitter_failed：clean提高3.133个百分点，bit增加4.345%。

30景看门狗在NACK也未送达时仍提供有限兜底，因此保留了可测量价值。

## 5. 安全性与可复现性

四类策略、四类剖面均满足：

- 发送端内部状态读取计数：0；
- 未计费反馈状态转移：0；
- 错误上下文执行：0；
- 旧恢复误接收：0；
- 总bit与各帧分量精确相等。

确认结果重复运行后，除完成时间外逐字段完全一致。

迁移到E盘后，全量回归有3项外部数据依赖失败：F盘AERPAW manifest和未迁移的 `data/raw/sigmf_5g_short`。排除这3个数据依赖测试文件后，其余代码回归全部通过；阶段9.5新增6项测试全部通过。没有复制或伪造缺失数据。

## 7. 研究贡献与边界

本阶段的主要贡献不是增加一个32 bit控制包，而是完成三点修正：

1. 将发送端信念更新约束为严格的已送达帧因果关系；
2. 把阶段9.1隐含oracle替换为显式、可丢失、可计费的控制反馈；
3. 在安全标签、任务性能和总bit之间建立可复现的端到端工作点。

RESET-NACK目前没有加密认证，不能抵抗恶意伪造；32 bit结构只验证软件位宽和字段一致性。当前结果也没有验证实际无线时延、板载进程调度、功耗或真实反馈链路故障。

## 8. 下一步

阶段9.6应将发送端和接收端拆成两个真实操作系统进程，通过网络代理分别注入前向丢包、反馈丢包、乱序、进程终止和目录损坏，并传输真实32 bit RESET-NACK与80/419 bit恢复帧。

在阶段9.6之前，S9-CRN32-HBW30-v1只作为确认通过的软件协议候选；具有外部频谱数据边界的主冻结架构仍为 S6R-FH10-v1。
