## 1. 研究目的

阶段9.8证明8-bit固定模式头能降低UDP应用载荷，但B2/B4批处理当时只有理想bit上界。阶段9.9进一步回答：实际任务更新是稀疏事件，当发送端必须等待第2个或第4个更新事件时，节省的头部bit是否足以抵偿接收端继续执行旧动作造成的损失。

## 2. 实验流程

实验首先生成B1即时发送的因果更新序列，再让B2和B4重放完全相同的更新项：

`连续频谱功率 → 多查询任务状态 → ε安全码字/escape动作 → B1更新事件 → B2/B4延迟重放 → 接收端动作regret`

一个含m个更新项的数据报位宽为：

`B(m) = 8 + 8 × ceil(42m ÷ 8) bit`

B2/B4只能在收到完整批次后执行最新动作。时间组末尾的残余项仍计费，但不能倒推改善已经结束的场景。该定义保持在线因果性，不读取未来频谱。

## 4. 为什么“B2最多等待1景、B4最多等待3景”不成立

阶段9.8的上界隐含假设更新每景出现。真实轨迹中的更新是稀疏且不规则的，所以“等待一个更新事件”不等于“等待一个场景”。

本次观察到：

- B2最大等待45景、698秒；
- B4最大等待55景、853秒；
- 12:30时间组中，N = 16/32/64的B2和B4 clean都只有39.66%。

因此，批大小只能限制等待的事件数，不能限制物理等待时间。接收端在等待期间持续使用旧动作，形成大量超出ε = 0.2 dB的过时动作场景。

## 6. 统计与复现审计

评测以时间组为配对分析单位，执行5000次组bootstrap。N = 8有一个时间组没有更新事件，因此bit节省区间下界保守地为0；但是否保留并不依赖这一边界，因为clean下降已经达到23.35个百分点。

确认与独立复现的规范化结果散列均为：

`65c3939f3248438edd412d04a7a2b658cb3073874c8e6b6b299250c70aab4d8a`

首次确认运行曾在“bootstrap样本全部来自零更新组”时触发除零并在结果写出前停止。修复只把无更新机会的bit节省定义为0，并新增边界测试；没有更改数据、候选、任务阈值或保留门槛。

## 8. 冻结结论

B2和B4均不进入主架构。阶段9.9证明：对单一接收端的实时顺序动作流，依靠累计后续事件来摊薄数据报头，会把有限的bit收益转换为过大的动作陈旧风险。

当前继续保留：

- `S9-CH8-v1`：单更新、8-bit固定模式UDP头；
- 已有上下文身份检查、RESET-NACK和fail-closed恢复；
- 阶段6外部Final失败结论不变。

纯头部压缩和顺序更新批处理到此停止。下一步应完成阶段9协议证据收口；新的算法研究只有在获得新外部连续频谱数据或真实硬件/链路轨迹后才有充分依据，不应继续在同一pilot时间组上扫描新的等待阈值。
