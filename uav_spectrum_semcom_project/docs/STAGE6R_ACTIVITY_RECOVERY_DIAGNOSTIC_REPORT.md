# 阶段6R逐活动稳定性、会话摊销与恢复安装归因报告

## 1. 研究目的

S6R.3c 已经表明：在四个开发活动按场景数合并时，clean = 0.90 下四种 N 都有正的总 bit节省。

本阶段继续检查三个问题：

1. 正收益是否在不同活动之间稳定；
2. 正收益是否依赖较长会话对安装开销进行摊销；
3. 恢复安装主要由哪些链路和上下文故障产生。

所有分析严格复用 S6R.3c 已选的 clean = 0.90 工作点和时序码本动作，不重新选择可靠性参数，不重新拟合动作元组，不访问新 Final。

## 2. 逐活动与会话长度诊断

### 2.1 一致性检查

完整活动条件下，本阶段重新运行的四种 N 均精确复现 S6R.3c 的：

- 语义 clean 点估计；
- 语义总 bit/景；
- 精确基线 clean；
- 精确基线总 bit/景。

所有错误码本动作执行次数为 0，Final 访问次数保持 1。

### 2.2 场景加权与等活动宏平均

| N | 场景加权节省 | 等活动宏平均节省 | 二者差值 |
|---:|---:|---:|---:|
| 8 | 3.61% | −16.09% | −19.70个百分点 |
| 16 | 4.83% | −20.32% | −25.14个百分点 |
| 32 | 8.29% | −16.45% | −24.74个百分点 |
| 64 | 10.58% | −4.80% | −15.38个百分点 |

场景加权和等活动宏平均的方向在四种 N 上全部相反。

原因是 2023 活动包含 364 景，占总 564 景的 64.5%；其安装开销可以在较长会话中摊薄，而三个 2024—2025 活动分别只有 66—67 景。

### 2.3 单活动结果

| N | 2023节省 | Lake Wheeler 2024 | Packapalooza 2024 | Packapalooza 2025 |
|---:|---:|---:|---:|---:|
| 8 | 21.21% | −7.46% | −30.18% | −47.93% |
| 16 | 27.30% | −19.86% | −29.86% | −58.85% |
| 32 | 30.43% | −19.80% | −30.17% | −46.23% |
| 64 | 24.34% | 0.81% | −16.24% | −28.11% |

除了 N = 64 的 Lake Wheeler 2024 点估计接近 0，其余短活动均为负。排除 2023 活动后，四种 N 的聚合节省全部显著为负。

因此 S6R.3c 的结论必须收缩为：

> clean = 0.90 下的场景加权正收益成立，但主要由长会话活动主导，尚不能称为跨活动稳定收益。

### 2.4 冷启动会话长度

下表给出每个分段会话都重新校准并安装上下文时的场景加权节省。

| 会话长度 | N = 8 | N = 16 | N = 32 | N = 64 |
|---:|---:|---:|---:|---:|
| 20景 | −38.23% | −55.73% | −51.35% | −29.59% |
| 50景 | −13.30% | −22.15% | −16.34% | −1.88% |
| 100景 | −2.35% | −4.44% | −1.07% | 5.32% |
| 完整活动 | 3.61% | 4.83% | 8.29% | 10.58% |

只有 N = 64 在 100 景时获得置信下界高于 0 的正收益；N = 8、16、32 在已注册的有限会话长度中均没有稳定的冷启动 break-even 点。

这说明当前方案更适合：

- 长时间持续工作的无人机链路；
- 码本和上下文可以跨任务片段保持的系统；
- N 较大、精确动作索引本身较宽的任务。

当前方案不适合直接宣称：

- 短突发任务必然节省总 bit；
- 每次起飞或每个业务片段都冷启动时仍有优势。

## 3. 恢复安装故障归因

### 3.1 方法

对以下五个因素运行全部 32 个开关组合：

- 安装包丢失；
- 任务包丢失；
- ACK 丢失；
- 延迟重复 ACK；
- 接收端上下文重置。

使用 Shapley 分解将主故障条件相对无故障条件的增量分配给各因素。所有指标的效率残差均不高于 10⁻¹⁰。

该归因描述注册仿真器中的贡献，不等价于真实部署中的因果效应。

### 3.2 恢复安装 bit归因

单位均为 bit/景。

| 因素 | N = 8 | N = 16 | N = 32 | N = 64 |
|---|---:|---:|---:|---:|
| ACK丢失 | 16.13 | 15.23 | 14.81 | 17.76 |
| 接收端重置 | 6.58 | 5.76 | 6.03 | 6.27 |
| 任务包丢失 | 7.12 | 1.13 | 1.10 | 7.82 |
| 安装包丢失 | 0.54 | 0.58 | 0.68 | 0.66 |
| 延迟重复ACK | 0.00 | 0.00 | 0.00 | 0.00 |
| 合计恢复安装 | 30.36 | 22.69 | 22.61 | 32.50 |

ACK 丢失是四种 N 上一致的第一大恢复安装来源。

N = 8、64 的任务包丢失贡献更高，是因为 clean = 0.90 的入选点采用单次任务包；N = 16、32 使用两次任务包，降低了任务更新不确定性，但增加了重复任务帧开销。

### 3.3 总 bit增量归因

ACK 丢失对总 bit增量的贡献约为 18.20—20.67 bit/景；接收端重置约为 6.67—7.35 bit/景。延迟重复 ACK 不增加恢复安装，但会增加约 2.26—2.33 bit/景的反馈开销。

ACK 丢失对任务失败概率的 Shapley 值略为负，并不意味着 ACK 丢失有益。其原因是：

- ACK 缺失使发送端采用更保守的上下文信念；
- 更频繁恢复安装偶尔减少了不可用持续时间；
- 该数值包含协议交互，不是独立因果效应。

这个负归因必须保留，不能删除或解释为系统应主动丢弃 ACK。

## 4. 64 bit短激活帧工程反事实

### 4.1 两种反事实

已知码本方案：

- 只将 `BANK:*` 活动的完整安装和恢复安装替换为短激活帧；
- OOD 适配码本仍使用完整安装。

全部缓存方案：

- 已知 BANK 使用短激活帧；
- OOD 首次安装仍发送完整码本；
- OOD 后续恢复假设可从本地缓存短激活。

两种方案都保持原安装包的丢失概率和 ACK 行为不变，因此只表示 bit账本上限，不表示已实现协议。

### 4.2 64 bit结果

| N | 已知码本场景加权 | 已知码本宏平均 | 全部缓存场景加权 | 全部缓存宏平均 |
|---:|---:|---:|---:|---:|
| 8 | 26.31% | 31.97% | 51.53% | 41.74% |
| 16 | 22.21% | 16.48% | 39.87% | 23.32% |
| 32 | 25.08% | 19.09% | 41.71% | 25.53% |
| 64 | 31.44% | 39.33% | 55.35% | 48.59% |

已知码本方案和全部缓存方案均通过执行前登记的开发入口门。即使只替换三个 `BANK:*` 活动，四种 N 的等活动宏平均也全部转正。

这说明短激活协议具有足够大的潜在收益，值得进入正式实现。

### 4.3 不能直接采用反事实数字的原因

真实协议还必须解决：

- 码本目录版本；
- bank ID 与完整清单哈希的绑定；
- 激活 epoch；
- ACK 对哪次激活生效；
- 设备重启后本地码本是否仍存在；
- 目录失配时的 fail-closed 行为；
- OOD 新码本首次完整安装与后续缓存恢复；
- 短激活帧丢失、重复和乱序。

只有这些机制实现并进入状态机后，才能重新报告 matched-clean 总 bit。

## 5. 阶段结论

S6R.3d 得到一项正结果和两项重要限制：

正结果：

> 64 bit版本化短激活协议具有明确的开发价值，值得实现。

限制一：

> 当前 full-install 方案的正收益依赖长会话，尚未跨活动稳定。

限制二：

> 恢复安装主要由 ACK 不确定性驱动；仅继续压缩码字或改进轻量排序器不能解决该问题。

因此下一阶段 S6R.3e 的优先级为：

1. 实现固定 64 bit版本化码本激活消息；
2. 建立接收端预装码本目录；
3. 只有目录 epoch、bank ID 和码本 tag 全部匹配时才激活；
4. 使用累计 ACK 确认激活 epoch；
5. 失配时拒绝紧凑动作并回退完整安装；
6. 将该协议接入完整可靠性状态机；
7. 重新执行逐活动和会话长度 matched-clean 验证。
