# 阶段9软件在环实验预注册

## 1. 研究问题

本阶段验证：当接收端进程重启可以被软件显式观测时，由接收端上报启动身份并触发恢复，能否在任务可靠性基本不下降的条件下，比阶段6冻结的固定10景心跳减少总控制开销。

候选方法记为 S9-BER-v1。它不改变任务码本、regret 判决、精确动作 escape 或 fail-closed 安全边界，只改变“接收端重启后如何被发现”。

## 2. 软件在环边界

实验建立独立接收端进程、持久化目录和可控双向链路。可以模拟：

- 接收端进程崩溃与重新启动；
- 保留码本目录的热重启；
- 丢失持久化目录的冷重启；
- 前向包丢失、反馈包丢失和突发中断；
- 动作缓存、更新序号和进程身份的生命周期；
- 恢复时延、不可用时间和完整协议 bit。

本实验不能证明真实无人机的 CPU、功耗、射频链路、操作系统故障率或存储可靠性。所有结果均标记为软件在环工程证据，不标记为外部 Final。

## 3. 比较方法

1. fixed10：每静默10景发起一次32 bit 探测，并接收32 bit 响应。
2. boot_event：进程启动后重复发送64 bit 启动状态，直到恢复更新被确认。
3. no_heartbeat：不主动检测启动，仅在紧凑更新缺少 ACK 后恢复。
4. stateless_exact：每景发送自包含精确动作，作为无状态高开销参照。

热重启保留预安装码本，但清空动作缓存；恢复需要64 bit 激活、42 bit 紧凑更新和24 bit ACK。冷重启还需发送完整码本安装。42 bit 来自40 bit 固定头部和阶段7最终冻结 K=3 码本所需的2 bit 符号。所有策略在未恢复上下文前均禁止执行旧动作。

版本说明：最初的 v1 注册误用了阶段6早期 K=4 位宽，审计发现与阶段7最终冻结不一致后，v1 被判定为协议不匹配，不作为正式证据。v2 在不改变故障模型、统计门槛和比较方法的前提下纠正位宽，并重新执行完整开发—冻结—确认流程。

## 4. 主要指标

- 总 bit/景；
- clean rate 与 availability；
- 错误上下文动作执行次数；
- 重启到重新可用的恢复时延；
- 启动上报、心跳、安装、更新和 ACK 的分项开销。

主比较采用相同随机轨迹和相同故障轨迹的配对设计。S9-BER-v1 只有同时满足以下条件才通过：

- clean rate 差值的95%置信区间下限不低于 −0.5 个百分点；
- 相对总 bit 节省的95%置信区间下限高于5%；
- 错误上下文动作执行次数为0；
- 恢复时延95分位数不劣于 fixed10；
- 四类故障中至少三类通过。

## 5. 数据隔离与冻结

开发阶段只使用预注册的合成任务动作轨迹。开发完成后冻结候选、代码哈希和参数，再使用独立种子执行一次确认性模拟。阶段6和阶段8已经消费的确认数据不会读取，确认性模拟结果也不用于再次调参。

## 6. 结论解释

若候选通过，只能说明“显式启动事件在注册的软件故障模型中优于固定心跳”，不能直接宣称真实板载系统有效。若失败，保留 fixed10，说明事件恢复没有形成稳定的新贡献；若所有有状态方案均被无状态方案支配，则需要重新评估短会话下维护接收端上下文的必要性。
