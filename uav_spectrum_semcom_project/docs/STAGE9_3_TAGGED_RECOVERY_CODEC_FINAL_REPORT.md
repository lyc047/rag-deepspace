## 2. 协议设计

### 2.1 恢复会话身份

恢复会话身份由以下字段构成：

- 发送端控制器代次：8 bit；
- 接收端 boot ID：16 bit；
- 目录版本：8 bit。

将固定宽度身份与协议域分隔符拼接，计算 SHA-256，并取前16 bit作为恢复标签。恢复帧到达时，接收端必须使用“当前”boot ID、控制器代次和目录版本重新计算标签，不能只相信启动状态上报时的旧值。

16 bit标签发生随机碰撞的单次概率约为1/65,536。它只用于发现偶发旧会话，不是消息认证码；面对主动伪造时必须换成带密钥MAC或更长认证标签。

### 2.2 帧宽

| 帧类型 | 原宽度 | 新宽度 | 变化 |
|---|---:|---:|---:|
| 预安装码本激活 | 64 bit | 80 bit | +16 bit |
| 完整安装，N = 32、K = 3 | 403 bit | 419 bit | +16 bit |
| 普通紧凑更新 | 42 bit | 42 bit | 不变 |
| 累计ACK | 24 bit | 24 bit | 不变 |

额外开销只出现在恢复帧。相对单帧看，激活帧增加25%，完整安装增加3.97%；长期平均开销仍取决于实际恢复频率。

### 2.3 接收端安全机制

接收端实现了：

1. 恢复到达时二次核对当前 boot ID、目录版本和标签；
2. 持久目录使用完整 SHA-256封装校验；
3. 文件损坏、字段缺失或无法解析时 fail-closed；
4. 8 bit更新序号采用半窗口规则：仅当 0 < Δ mod 256 < 128 时接受为新包；
5. 完全相同的当前包允许幂等接收；
6. 延迟包最大寿命为127次更新；
7. 恢复会话变化时清空旧队列；
8. 冷启动、热启动和双端同时重启后均先失活，再完成合法恢复。

## 3. 实验设计

### 3.1 预注册与冻结

开发前固定：帧字段、标签算法、故障事件、200条开发轨迹、500条确认轨迹、每条200步、随机种子和零违例门槛。开发通过后，配置、源码、worker、实验脚本和单元测试均写入 SHA-256冻结清单，确认运行前逐文件复核。

### 3.2 三层验证

第一层验证二进制帧精确宽度、往返解析和错误身份拒绝。

第二层启动3个不同PID的接收端进程，覆盖冷完整安装、热激活、上一boot旧恢复、上一控制器旧恢复、错误目录、254→255→0回绕、回绕前旧包、重复包、队列清空、128次寿命越界、持久文件损坏和双端同时重启。

第三层进行随机事件交错。确认集共100,000步，12类事件各出现约8,200至8,500次，不读取任何频谱 Final 或外部确认数据。

## 6. 有效贡献与仍未解决的问题

### 6.1 本阶段形成的正向成果

- 修复了“启动状态到达后、恢复包到达前再次重启”的竞态；
- 证明恢复标签能够兼容现有64 bit激活和403 bit完整安装codec；
- 普通高频更新与ACK不增加标签开销；
- 将目录损坏、串号回绕和旧队列从文字约束落实为可执行拒绝逻辑；
- 使阶段9.2的符号结论具备真实进程证据。

### 6.2 结论边界

- 16 bit标签可能碰撞，不能用于对抗恶意伪造；
- 包寿命小于128次更新和恢复时清队列是必要前提；
- 当前worker是桌面进程，不是无人机板载实现；
- 当前实验没有测量clean rate、频谱regret、功耗或真实链路时延；
- 阶段6外部 Final 仍为失败，主冻结架构仍是 S6R-FH10-v1。

## 7. 下一步：阶段9.4端到端协议栈集成

下一步不增加新机制，而是将 S9-RCV2-v1 接入 S9-HBW30-v1 的完整发送端—接收端循环，回答“安全标签实现是否在保持零错误上下文的同时，只产生预期恢复开销”。

执行顺序：

1. 冻结适配层：boot事件生成控制器代次、boot ID和目录版本；
2. 用标签激活/完整安装替换旧恢复调用，普通42 bit更新和24 bit ACK保持不变；
3. 将队列寿命与清空规则接入丢包、乱序和延迟代理；
4. 复跑阶段9.1四类注册故障，不重新扫描看门狗间隔；
5. 比较旧 HBW30 与标签 HBW30 的clean、总bit、恢复时延和错误上下文执行；
6. 验证实测额外bit是否等于16 × 恢复帧次数；
7. 若通信栈不能保证127次寿命界限，停止使用仅恢复标签并切换全包标签；
8. 通过后再将其列为等待硬件在环验证的协议候选。
