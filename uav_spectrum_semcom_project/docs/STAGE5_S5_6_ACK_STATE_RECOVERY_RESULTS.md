## 1. 问题

前序算法默认发送端与接收端通过ACK共享同一状态。真实协议中可能出现：

- 更新包成功到达，但ACK丢失；
- 旧ACK延迟后重复到达；
- 数据包失败和ACK丢失对发送端都表现为“没有收到确认”；
- 8-bit状态纪元从255回绕到0。

如果发送端相信的状态与接收端实际状态不同，发送端计算的复用regret就不再对应接收端真正复用的块。S5.6显式分离两套状态，检查这一假设是否破坏算法。

## 2. 方法

主压力输入固定为S5.5中最困难的“频段跃迁 + Markov查询”。τᵣ = 0.2 dB、Aₘₐₓ = 120 min保持不变。

比较四种协议：

1. `ideal_ack`：无ACK故障的参考；
2. `naive_ack`：ACK丢失后继续使用旧信念，并接受延迟旧ACK；
3. `epoch_guard`：用8-bit串行纪元拒绝重复或过期ACK；
4. `uncertainty_recovery`：纪元保护之外，只要一次发送没有得到有效确认，就持续发送绝对多查询包，直到收到有效ACK。

纪元比较采用有限序列规则。设候选纪元为e、新旧确认纪元为e₀，则：

e比e₀更新，当且仅当 0 < (e − e₀) mod 256 < 128

因此0可被判定为255之后的新纪元，而255不会被误判为0之后的新纪元。

ACK丢失概率为0、5%、10%和20%，延迟重复ACK概率为0或10%，形成8个冻结条件。数据链路仍覆盖AWGN、Rayleigh、Rician和Eᵦ/N₀ ∈ {0, 3, 6, 9} dB。

## 4. 机制结论

### 4.1 纪元保护解决重复ACK回退

当ACK不丢失但有10%重复ACK时，天真协议状态分叉率为5.7%；纪元保护将其降至0，并相对天真协议降低2.18%的实际bit。旧ACK会使天真发送端回到较早状态，随后产生额外发送和任务损失。

### 4.2 纪元保护不能单独解决ACK丢失

没有重复ACK时，`epoch_guard`与`naive_ack`结果完全相同。因为ACK丢失并不是“收到旧纪元”，而是根本没有可验证的新确认。

### 4.3 不确定状态强制刷新在中高故障率下有效

ACK丢失达到5%—20%时，自愈协议在无重复ACK条件下全部通过。其额外bit只有4.45%—5.61%，但平均和尾部regret均显著下降。

### 4.4 低故障下存在过度恢复

即使ACK故障概率为0，数据包失败也会造成“无ACK”。自愈协议无法区分数据包失败和ACK丢失，因此强制恢复率达到18.9%，增加4.02%的bit，且CVaR点估计略差0.00292 dB。当前“一次未确认就立即持续刷新”的规则过于激进。

## 5. 推断边界与谬误扫描

总体置信度为 **CAUTION**。结果识别了真实的协议逻辑缺口，但ACK故障来自注入模型。

## 6. 当前结论

可以陈述：

> 8-bit纪元保护能够阻止延迟重复ACK造成的状态回退；当ACK丢失率为5%—20%时，不确定状态强制绝对刷新能以不超过5.61%的额外bit降低平均和尾部regret，但当前单次未确认即恢复的规则在低故障条件下过于激进，预注册门槛仅有4/8条件通过。

不能陈述：

- ACK状态问题已经全部解决；
- 自愈协议已经可以冻结进入独立Final；
- 注入的ACK丢失率代表真实无人机链路；
- 阶段四或阶段五Final已经运行。

## 8. 下一步

下一版不扩大故障网格，而是设计低开销的迟滞恢复：

1. 第一次未确认只进入“可疑”状态；
2. 连续两次未确认或状态年龄接近上限时才强制绝对刷新；
3. 收到新纪元ACK立即退出恢复；
4. 继续保留旧ACK拒绝；
5. 与当前立即恢复、纯纪元保护和理想ACK比较。

目标是在保留中高ACK故障收益的同时，消除无故障和低故障条件下的过度发送。
