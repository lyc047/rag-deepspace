## 1. 目的与冻结条件

S5.2检验S5.1算法是否依赖固定需求。接收端查询在 D ∈ {2, 4, 6} 之间变化，每个需求维护独立的ACK同步状态。S5.1选出的

τᵣ = 0.2 dB，Aₘₐₓ = 120 min

保持不变，没有针对动态任务重新调参。

两种冻结查询序列为：

1. `cyclic`：每个站点按 2 → 4 → 6 周期切换，并采用不同起点平衡总体数量；
2. `markov`：需求保持概率为0.7，其余概率转移至其他需求，模拟具有持续性的业务。

查询序列是生成的实验输入，不是真实用户业务日志。

事件触发差分相对每景绝对索引：

- 实际bit降低26.33%；
- 平均regret差为+0.01820 dB，单侧95%上界0.02503 dB；

固定周期方法无法节省bit，因为每种需求再次出现时其独立状态已经达到刷新周期。

## 3. 结论

动态需求实验不是单一“成功”或“失败”，而是识别了查询持续性条件：

> 按需求维护独立状态的方法在业务需求具有时间持续性时有效；当不同带宽需求逐景轮换时，每个缓存状态的复用间隔扩大，导致发送率和陈旧风险同时增加。

因此，后续不应只重新调节 τᵣ 或 Aₘₐₓ。更直接的架构改进是：

> 每次触发时利用同一功率扫频同时计算多个需求的最优块，并把多查询决策打包，使一次成功传输刷新全部需求状态。

对于 N = 8、D ∈ {2, 4, 6}，多查询绝对索引载荷为

⌈log₂ 7⌉ + ⌈log₂ 5⌉ + ⌈log₂ 3⌉ = 3 + 3 + 2 = 8 bit

虽然比单查询的2—3 bit更长，但有可能通过显著减少未来更新次数降低总链路成本；是否跨越FEC边界必须由真实codec实验判断。

## 4. 统计与边界

- 两种查询序列均完整报告，没有只保留通过门槛的Markov结果；
- 参数来自S5.1并保持冻结，S5.2没有再次优化；
- 统计单位仍为72个“站点×本地小时”簇；
- 结果仍来自同一AERPAW活动和仿真回传链路；
- `cyclic`是压力测试，不代表真实需求分布；
- `markov`转移矩阵是建模假设，不是从业务数据估计。
