## 1. 结论

阶段9.4完成了 S9-RCV2-v1 与 S9-HBW30-v1 的端到端集成，但候选未通过预注册开发门槛，因此停止在开发阶段，没有冻结，也没有运行确认种子。

结果不是“16 bit标签太贵”。标签 HBW30 与零标签影子协议在所有轨迹上的任务结果完全相同，且新增bit严格等于16乘以恢复帧次数。失败来自因果身份同步：接收端重启后，如果64 bit启动状态未成功送达，发送端不知道当前 boot ID，安全协议只能等待30景看门狗；阶段9.1旧模拟器却能直接读取接收端内部的恢复接受状态和目录状态，从而在没有显式反馈bit时提前恢复。

因此，阶段9.4发现并修正了阶段9.1证据链中的一个因果信息泄漏。阶段9.1在启动发送器正常的两类结果基本保持成立；其在启动发送器退化和完全失效条件下的正向结论不再作为有效协议证据。

## 2. 实验设计

### 2.1 固定条件

直接复用阶段9.1的：

- 1000景任务长度；
- 三个任务语义符号；
- 0.08符号变化概率；
- 四类故障剖面；
- 前向、反馈、突发丢包和重启参数；
- 30景看门狗；
- 42 bit普通更新和24 bit ACK。

未扫描任何故障率、看门狗间隔或非劣阈值。

### 2.2 五路配对

每条任务轨迹和故障轨迹同时用于：

1. 16 bit标签 HBW30；
2. 0 bit标签影子协议；
3. 阶段9.1旧 HBW30；
4. 阶段9.1旧 fixed10；
5. 阶段9.1旧 boot-event。

影子协议执行完全相同的安全状态机，只将标签计费设为0，用于避免把因果控制流程变化误算为标签开销。

## 3. 开发过程中的实现修正

第一次开发运行中，普通更新丢失会错误触发 `begin_recovery`，使仍有效的缓存动作主动失活。这与协议定义不符。该结果保留为 `development_result.json`。

修正后，只有真实boot变化或已送达状态响应才建立新恢复会话。普通更新丢失只进入重传，不主动销毁有效上下文。修正后的结果保存为 `development_result_v2.json`，并以同一开发种子完整复现；除完成时间外逐字段相同。

这次修正不改变30景间隔、故障参数、确认种子或验收阈值，属于明确的实现错误修复。

## 6. 阶段9.1证据更正

旧模拟器存在两处不满足严格因果实现的行为：

1. 发送端直接读取 `receiver.restore()` 或 `receiver.update()` 的内部返回值，即使没有收到相应反馈bit也能改变协议状态；
2. 当更新遇到已重启的接收端时，发送端能够直接知道接收端不活跃和目录情况，并在下一景完整恢复。

在实际通信系统中，发送端只能依据成功接收的启动状态、ACK、NACK或看门狗响应改变信念。阶段9.4删除这类内部真值后，启动发送器故障条件的原正结果消失。

该发现不否定阶段9.1真实进程对冷启动、热启动、目录损坏和旧包拒绝的安全检查；它否定的是“启动状态不可用时仍能保持原clean收益”的端到端性能解释。

## 8. 下一步：阶段9.5显式因果反馈协议

阶段9.5不继续修改标签，而是重构所有发送端状态转移：

1. 发送端不得读取接收端函数返回值，只能读取实际送达的控制帧；
2. 将异步启动公告故障与普通反馈链路故障分开建模；
3. 定义并计费 `RESET-NACK`，在失活接收端收到普通更新时返回当前 boot ID、目录版本和状态；
4. NACK丢失时仍由30景看门狗兜底；
5. ACK、NACK、启动状态和看门狗响应分别进入发送端信念状态机；
6. 首先验证因果闭包和零内部真值访问，再比较 clean–bit；
7. 若显式NACK仍不能恢复原价值，则接受安全性—可用性权衡，不继续增加隐含oracle。

在阶段9.5通过前，阶段9.1和9.4均不生成新的主冻结协议；当前主冻结架构仍为 S6R-FH10-v1。
