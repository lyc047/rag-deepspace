## 1. 研究问题

阶段9.6不再用同一Python对象模拟收发双方，而是检验：阶段9.5的32 bit RESET-NACK和阶段9.3的标签恢复帧，能否在独立发送端进程、独立接收端进程与故障注入网络代理之间保持因果一致、安全关闭和精确计费。

本阶段不读取频谱Final，也不调整阶段6主算法。

## 2. 预先冻结的协议对象

- 32 bit RESET-NACK：反馈接收端boot ID、目录版本和失败原因；
- 80 bit标签激活帧：接收端已有正确持久码本时，激活预安装码本；
- 419 bit标签完整安装帧：接收端无目录或目录损坏时，重新安装码本；
- 42 bit紧凑更新帧：在码本上下文已恢复后传输当前任务动作。

特别约束：80 bit激活帧和419 bit完整安装帧都不携带当前动作。因此，即使上下文帧被正确接收，接收端也必须保持不可执行，直到随后收到并验证42 bit更新帧。若实验代码在未收到更新时直接恢复动作，即判定存在未传输信息泄漏。

## 3. 进程与网络边界

发送端和接收端必须拥有不同操作系统PID。协议bit先按高位优先方式打包为字节，再通过JSONL进程管道传给网络代理；JSON仅作为试验控制包络，不计入协议空口bit。代理保存原始bit长度和字节，不得重新调用编码器生成延迟包。

代理可执行送达、丢弃、延迟、乱序和单bit破坏。丢弃包不得产生目的端状态转移；反馈包未送达时，发送端信念不得变化。

## 4. 注册故障场景

1. 冷启动后请求419 bit完整安装，安装后仍不可执行，再用42 bit更新恢复；
2. 热启动后请求80 bit激活，激活后仍不可执行，再用42 bit更新恢复；
3. 丢弃RESET-NACK后发送端状态不变；
4. 接收端二次重启后，上一boot的延迟恢复帧被拒绝；
5. 更新序号从254跨越到0后，乱序送达255被拒绝；
6. 终止并重启接收端进程，PID变化且易失动作清空；
7. 终止并重启发送端进程，PID变化且必须重新依赖显式反馈；
8. 持久目录校验损坏后不可执行，完整安装可恢复；
9. 截断、非法填充或单bit破坏的帧被拒绝；
10. 全部实际传输帧进入代理计费账本。

## 5. 开发、冻结与确认

开发种子为20261701，除确定性场景外执行200次注册随机故障操作。开发门槛通过后冻结源码、配置、测试与开发结果散列，之后才允许使用确认种子20261801执行500次随机故障操作。

确认门槛为：注册场景通过率100%，帧宽完全一致，错误上下文执行、旧恢复误接收、旧更新误接收、目录损坏后执行、丢失反馈导致发送端变化、未计费线上帧和随机故障安全违例均为0。确认结果还必须在排除PID和时间戳后可复现。

## 6. 结论边界

正结果只说明桌面操作系统上的二进制协议实现与注册状态机一致。它不代表真实无人机板载时延、功耗、驱动队列、无线传播或故障概率，也不改变阶段6外部Final的负结论。16 bit标签只用于偶发旧会话检测，不具备对抗攻击的认证能力。
