## 1. 研究问题

阶段9.7检验：阶段9.6已经确认的二进制因果恢复协议，在发送端、故障代理和接收端分别作为三个独立操作系统进程，并通过真实IPv4环回UDP数据报传输时，能否继续满足安全关闭、因果反馈、旧包拒绝与精确计费要求。

本阶段不使用频谱Final，不改变频谱选择、任务码本、regret阈值或心跳策略。

## 2. 数据平面与控制平面

试验主控通过JSONL命令控制三个工作进程，但任何RESET-NACK、激活、安装和任务更新均不得通过JSONL传递。协议帧必须由发送进程打包为UDP数据报，经UDP代理进程处理后，再由接收进程从套接字读取；反馈方向相同。

每个数据报增加32 bit试验传输头：8 bit魔数、4 bit版本、4 bit类型和16 bit协议有效长度。该传输头不是阶段9.5语义协议的一部分，因此分别统计原协议bit与UDP应用载荷bit。

注册宽度如下：

| 帧 | 原协议 | UDP应用载荷 |
|---|---:|---:|
| RESET-NACK | 32 bit | 64 bit |
| 标签激活 | 80 bit | 112 bit |
| 标签完整安装 | 419 bit | 456 bit |
| 紧凑更新 | 42 bit | 80 bit |

UDP应用载荷包含字节对齐填充。由于本阶段不抓包，IPv4与UDP头部不作为实测流量报告。

## 3. 故障与场景

代理必须支持送达、丢弃、延迟后释放、乱序、重复和单bit破坏。进程层覆盖发送端重启、接收端热/冷重启、代理重启、目录校验损坏、接收超时和未注册源数据报。

确定性场景共11项，包括冷安装、热激活、丢NACK、旧恢复、序号回绕、重复幂等、数据破坏、未知源、代理重启和目录损坏。端点跨重启复用同一UDP端口，使代理队列中的旧包确实可以到达新进程并接受协议身份检查。

## 4. 开发、冻结与确认

开发使用种子20261901和100次随机操作；通过后冻结源码、测试、配置与开发结果散列。确认使用未提前运行的种子20262001和300次随机操作，并完整复现一次。

随机操作概率在实现试验前固定：普通更新60%，热重启12%，冷重启7%，丢NACK 5%，持久目录损坏5%，单bit破坏后重试5%，延迟乱序对6%。

## 5. 验收门槛

11项场景通过率必须为100%；三个进程PID不同且UDP端口非零；协议宽度与UDP应用载荷宽度完全匹配；错误上下文执行、旧恢复误接收、旧更新误接收、破坏包误接收、未知源转发、丢反馈导致发送端转移、端点已发但代理未记账的数据报和随机故障违例必须全部为0。

时延报告中位数、95%分位数和最大值，但它包含JSONL编排和桌面调度，不进入通过门槛，也不进入规范化复现散列。

## 6. 结论边界

正结果最多证明本机环回UDP及注册代理故障下的协议一致性。它不代表真实无人机、RF传播、蜂窝或Wi-Fi链路、板载功耗、网卡驱动队列或现实故障率，也不改变阶段6外部Final失败。阶段9.7是传输实现证据，不是新的频谱算法创新。
